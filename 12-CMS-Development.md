# Purpose

This chapter defines the engineering standards for developing frontend components that receive content from a Content Management System (CMS).

CMS-generated markup differs from developer-written markup because the HTML is controlled by the CMS rather than the frontend developer.

The frontend architecture must therefore be designed to remain stable regardless of how content changes over time.

---

# Objective

Frontend implementations should remain fully functional after content editors update the CMS.

Developers should build resilient HTML and SASS that does not depend on manually adding classes to CMS-generated elements.

The objective is to ensure:

- Maintainability
- Editor friendliness
- Consistent styling
- Long-term stability
- Reduced support effort

---

# Engineering Philosophy

The CMS owns the content.

The frontend owns the presentation.

Developers should never require editors to understand HTML or CSS in order for the website to render correctly.

Styling should adapt to CMS output—not the other way around.

---

# Mandatory Rules

Every CMS implementation MUST:

- Confirm which fields are CMS-controlled before development begins.
- Confirm which fields are Rich Text fields.
- Style content through wrapper selectors.
- Avoid styling directly on CMS-generated elements.
- Use pseudo-elements for decorative icons.
- Keep CMS markup clean.
- Preserve semantic HTML.
- Build reusable wrapper structures.

These rules are mandatory.

---

# CMS Planning

Before implementation begins, identify every CMS-controlled field.

Typical editable fields include:

- Page title
- Subtitle
- Rich Text content
- Images
- CTA buttons
- Lists
- FAQs
- Cards
- Testimonials
- Repeater content

Never assume which fields are editable.

Always confirm with:

- Client
- CMS developer
- Backend developer
- Project documentation

---

# Rich Text Fields

Rich Text editors generate their own HTML.

Typical output may include:

```html
<p></p>

<h2></h2>

<ul></ul>

<ol></ol>

<li></li>

<strong></strong>

<a></a>
```

Developers should expect this structure and design accordingly.

---

# Wrapper-Based Styling

Rich Text should always be styled through a wrapper.

Correct:

```sass
.content-wrp

    p
        color: $textColor

    h2
        margin-bottom: 24px

    ul
        margin-top: 24px
```

Incorrect:

```html
<p class="bodyText">
```

The CMS will not consistently preserve custom classes on generated content.

---

# Wrapper Responsibilities

The wrapper becomes the styling boundary for CMS output.

Typical wrappers include:

```text
content-wrp

editor-content

rich-text

cms-content
```

The wrapper should scope all typography, spacing, and list styling.

---

# Paragraph Styling

Paragraphs should inherit styling from the wrapper.

Example:

```sass
.content-wrp

    p
        font-size: var(--fs-body)
        color: $clr-body
        line-height: 1.8
```

Developers should never rely on:

```html
<p class="paragraph">
```

---

# Heading Styling

Heading elements should also inherit styles from the wrapper.

Example:

```sass
.content-wrp

    h2

    h3

    h4
```

Maintain a consistent hierarchy throughout CMS-generated content.

---

# List Styling

Lists generated by the CMS should be styled without modifying the HTML.

Correct:

```sass
.content-wrp

    ul

        li

            &::before
```

Incorrect:

```html
<li>

    <img>

    <i>

</li>
```

Decorative icons should never be inserted into editable CMS content.

---

# Decorative Icons

Decorative icons should be implemented using:

- `::before`
- `::after`

Never insert decorative markup into CMS-editable fields.

Reasons:

- Editors may accidentally delete it.
- CMS sanitizers may remove it.
- Content duplication becomes more difficult to manage.

---

# Repeater Content

Repeaters should output clean, semantic HTML.

Frontend styling should assume:

- Variable item counts
- Variable content lengths
- Optional fields
- Missing images
- Empty descriptions

Layouts should remain stable regardless of content variations.

---

# Image Fields

CMS-managed images should:

- Preserve aspect ratio
- Include meaningful alt text
- Support responsive sizing
- Avoid layout shifts

Never assume every image will have identical dimensions.

---

# CTA Fields

Buttons managed through the CMS should reuse the project's shared button component.

Only the following should typically be editable:

- Label
- URL
- Target

Button structure should remain controlled by the frontend.

---

# HTML Ownership

Editors should edit:

- Content
- Images
- Links

Editors should not manage:

- Layout
- Styling
- Decorative markup
- Structural wrappers

The frontend architecture should enforce this separation.

# Validation Checklist

Before implementation verify:

## Planning

- [ ] Editable fields confirmed.
- [ ] Rich Text fields confirmed.
- [ ] Repeaters confirmed.

---

## Structure

- [ ] Wrapper implemented.
- [ ] Semantic HTML preserved.
- [ ] No styling classes required inside CMS output.

---

## Styling

- [ ] Wrapper selectors used.
- [ ] Decorative icons use pseudo-elements.
- [ ] Typography scoped correctly.

---

## Content

- [ ] Long text tested.
- [ ] Empty fields tested.
- [ ] Variable item counts tested.
- [ ] Missing images tested.

---

## Accessibility

- [ ] Heading hierarchy maintained.
- [ ] Images include meaningful alt text.
- [ ] Links remain accessible.

---

# Common Mistakes

Avoid:

- Styling CMS paragraphs directly with classes.
- Inserting decorative HTML into editable fields.
- Assuming fixed content lengths.
- Assuming every image has the same dimensions.
- Building layouts that break when repeaters grow.
- Hardcoding CMS content into templates.
- Mixing frontend structure with editor content.

---

# Best Practices

- Confirm CMS fields before development.
- Build wrapper-based styling from the beginning.
- Test with realistic content.
- Test empty states.
- Test long content.
- Keep editor experience simple.
- Keep frontend architecture responsible for presentation.

---

# Engineering Acceptance Criteria

A CMS implementation complies with this standard when:

- Content editors can update content without breaking the layout.
- Rich Text is fully styled through wrapper selectors.
- Decorative elements are implemented through CSS.
- Layouts remain stable with variable content.
- CMS output remains semantic and maintainable.

---

# Chapter Summary

CMS integration requires a different engineering mindset than static HTML development.

By separating **content ownership** from **presentation ownership**, developers can build flexible, maintainable systems that remain stable as content evolves.

Wrapper-based styling, semantic HTML, and reusable structures are the foundation of successful CMS-driven frontend development.
